## Runtime Decisions

### D-001: Worktree structure — role-based, not phase-based
- **Date**: 2025-02-16
- **Context**: Needed to decide between disposable per-phase worktrees vs long-lived role-based ones
- **Decision**: 4 role-based worktrees (lead, ios, ml, review). Phases run sequentially within each worktree.
- **Alternatives**: Per-phase worktrees (more isolation but more merge overhead), single worktree with branches (simpler but no parallelism)
- **Impact**: Phases sharing files (e.g. VideoReviewLayoutView) run in the same worktree, eliminating merge conflicts

### D-002: Phase 1 and Phase 3 sequential in moveai-ios
- **Date**: 2025-02-16
- **Context**: Both phases modify `VideoReviewLayoutView.swift`
- **Decision**: Run sequentially in moveai-ios rather than in parallel
- **Alternatives**: Parallel with manual conflict resolution
- **Impact**: Simpler merge flow, no conflict risk on the most-edited file

### D-003: Patch-based review bundles + “no worker commits”
- **Date**: 2026-02-19
- **Context**: Need minimal human involvement with clean, reviewable handoffs.
- **Decision**: Workers do not commit by default. Workers produce `diff.patch/selfcheck.md/verify.md` bundles per TID; integrator applies patches in `moveai-review`, verifies, then commits.
- **Impact**: Clear handoff artifacts; integration happens in one controlled place.

### D-004: Suggested steps, binding objectives
- **Date**: 2026-02-19
- **Context**: Detailed step plans help, but shouldn’t prevent better solutions.
- **Decision**: Objectives + success criteria are binding; implementation steps are suggestions. Alternatives are encouraged if in-scope, minimal, and documented.
- **Impact**: Enables better technical choices while preserving scope control.

### D-005: Unlimited questions to understand objective
- **Date**: 2026-02-19
- **Context**: Agents need to understand UX intent to make correct local decisions.
- **Decision**: Agents may ask as many questions as needed; prefer batching. Non-blocking questions proceed with explicit defaults; blocking questions wait.
- **Impact**: Fewer wrong assumptions; better alignment with desired UX.

### D-006: Split Phase 2 into plumbing vs. computation
- **Date**: 2026-02-19
- **Context**: Phase 2 touches UI plumbing and view-model logic; we want parallelism without conflicts.
- **Decision**: Phase 2 becomes T-202 (plumbing/rendering) + T-203 (compute + wire highlights).
- **Impact**: Parallelizable work; reduced merge risk.

### D-007: Escape hatch — allow local commits via `series.patch`
- **Date**: 2026-02-19
- **Context**: Some tasks (rename-heavy diffs, repeated apply conflicts, or large changes needing incremental review) are awkward as a single staged diff patch.
- **Decision**: Default remains `diff.patch` with no worker commits. If needed, workers may create local commits (no push/merge) and deliver `series.patch` generated by `git format-patch`.
- **Impact**: Retains the default safety model while providing a pragmatic fallback for difficult-to-apply changes.

### D-008: README becomes index-only to prevent workflow drift
- **Date**: 2026-02-19
- **Context**: The README contained merge-based instructions that conflicted with the patch-based contracts.
- **Decision**: Keep `orchestrator/README.md` as an index + overview; canonical step-by-step lives in `review_checklist.md` and `integration_checklist.md`.
- **Alternatives**: Keep both flows with deprecation notes (higher drift risk), do nothing (agents follow wrong commands).
- **Impact**: DRY, lower confusion, fewer integration mistakes.

### D-009: Canonical, TID-based `selfcheck.md` template
- **Date**: 2026-02-19
- **Context**: Self-check requirements were duplicated between taskboard text and a legacy phase template, risking drift.
- **Decision**: A single canonical template (`orchestrator/templates/review_bundle_selfcheck_template.md`) defines required review sections, including architecture, DRY/quality, edge cases, security/privacy, tests, and performance.
- **Alternatives**: Keep multiple templates (higher drift), rely on free-form notes (lower consistency).
- **Impact**: More consistent reviews, fewer missing edge cases, reduced repetition.

### D-010: No-test-no-merge (with explicit waiver)
- **Date**: 2026-02-19
- **Context**: `verify.sh` ensures tests pass, but doesn’t guarantee new behavior is covered by new assertions.
- **Decision**: Every TID must add/upgrade at least one automated test that would fail pre-change, or explicitly request a waiver with compensating controls.
- **Alternatives**: Soft encouragement only (higher regression risk), require unit+UI always (higher cost/flake).
- **Impact**: Higher regression resistance with a pragmatic escape hatch.

### D-011: Lightweight performance gate
- **Date**: 2026-02-19
- **Context**: UI/video hot paths can regress performance without breaking tests.
- **Decision**: Require perf hot-path notes + at least one manual perf sanity scenario in `selfcheck.md`.
- **Alternatives**: Mandatory Instruments profiling (high overhead), no perf gate (higher jank risk).
- **Impact**: Catches obvious regressions without slowing iteration.
